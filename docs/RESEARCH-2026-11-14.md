# 图片上传、缓存与传输：2026-11-14 实验

优先方向是保留原生 WebSocket 增量传输，再对新图片生成稳定预览。反复重写完整历史有缓存代价；单纯扩大清退间隔也会增加累计上传。此次实现的是隔离研究原型，未替换默认 HTTP Guard，也未启用本机全局路由。

所有真实模型请求只包含生成的验证码图片，使用现有 Codex ChatGPT 登录。CLI 版本为 `0.166.0-alpha.5.1`，模型为 `gpt-6-astra`、low reasoning。这里验证的是该 CLI，不代表所有桌面版本、网络或账户的行为。公开数值见 [research-20261114.json](research-20261114.json)。

## 1. 原生 CLI 对本地模拟服务

同一张合成噪声图、六次工具往返、七次模拟生成；不调用真实模型。模拟服务的 token 数值没有统计意义，因此未作为 token 结果报告。

| 传输 | 累计请求载荷 | 图片发送次数 | 结果 |
|---|---:|---:|---|
| 完整 HTTP | 20,056,926 B | 7 | 通过 |
| 原生 WebSocket | 2,877,455 B | 1 | 通过 |
| WebSocket，中途注入一次状态丢失 | 5,743,590 B | 2 | 自动恢复后通过 |
| 0.1.0 Guard HTTP | 4,651,568 B | 7 次预览 | 通过 |

正常 WebSocket 的后续请求只有新增工具结果。模拟 `previous_response_not_found` 后，CLI 重新连接并发送完整历史，证明“通常只上传一次”需要服务端连接状态持续有效。这组本地模拟的 HTTP 与 WS 都未压缩，不能直接套用到真实线上编码比值。

这与 [官方 WebSocket 文档](https://developers.openai.com/api/docs/guides/websocket-mode) 的连接内增量和失效恢复机制一致。它解决重复传输，仍保留服务器上下文中的旧图片；不能由此认定 token 不再计入输入。

## 2. 真实服务的三张图探针

每张图包含一个清晰的四字符验证码。模型必须识别当前图并调用本地只读工具，才能取得下一张图；三次正确取图后结束。下表每行都完成三张图识别和四次生成。HTTP 使用实际 zstd 请求体；WebSocket 统计 UTF-8 消息载荷，不包含帧、TLS、TCP 或 VPN 开销。

| 方式 | 上传载荷 | 总输入 | 缓存输入 | 未缓存输入 | 输出 |
|---|---:|---:|---:|---:|---:|
| HTTP 原图，控制组 | 14.42 MB | 77,759 | 69,376 | 8,383 | 254 |
| 原生 WebSocket 原图 | 6.44 MB | 77,201 | 61,440 | 15,761 | 242 |
| HTTP 只压缩图片，不增加缓存提示 | 1.98 MB | 77,763 | 69,376 | 8,387 | 248 |
| Guard，提示仍放在每次请求末尾 | 1.98 MB | 78,299 | 37,504 | 40,795 | 261 |
| Guard，固定提示位置原型 | 1.99 MB | 78,099 | 61,824 | 16,275 | 254 |
| WebSocket + 稳定预览原型 | **0.94 MB** | 77,241 | 68,992 | **8,249** | 254 |

HTTP 控制组另两次为 8,383、8,365 未缓存输入，上传均约 14.42 MB。旧 Guard 直连的另一次为 35,316 未缓存输入；一组经过实验中转的 Guard 使用了五次生成，未混入上面的四次生成对照，原始汇总仍完整保留。

“WebSocket + 预览”这一轮比 HTTP 原图少约 93.5% 请求载荷，比只压缩的 HTTP 少约 52.5%，也没有移除任何历史图片。其未缓存输入没有出现此前 CAM 样本中的约 36% 增长。但这不是已经解决缓存成本问题的证明：本次没有随机化顺序、没有大量重复或长 MV 对照，原生 WebSocket 自身也出现过缓存命中波动。

总输入只变化几百 token，未缓存输入却可能变化数万。减少图片编码字节与减少图像 token 是不同问题；提示位置、历史改写、缓存可用性及额外工具往返都需要分开控制。固定提示位置的单次结果改善，尚不足以将全部差异归因于它。

[官方缓存文档](https://developers.openai.com/api/docs/guides/prompt-caching) 要求完整的渲染前缀匹配，同时查找边界和缓存可用性也影响命中。本报告没有把“前缀未变化”当作“保证缓存命中”，也没有用 API 单价换算 ChatGPT 订阅额度。所有成功探针报告的 cache-write token 均为 0，仍单独保留该字段。

## 3. 分批清退的离线对照

40 次请求逐张追加不同的 100×100 合成图；高水位 320,000 Base64 字节、低水位 160,000 字节、保留最近 1 张。两组均把同一个 scope 提示放在固定位置，以隔离清退策略影响。

| 指标 | 每次重新选择保留集 | 持续记录已移出图的原型 |
|---|---:|---:|
| 发生旧图片变化的请求 | 33 | 7 |
| 改变的旧图片位置总数 | 37 | 35 |
| 保留整个上一请求输入前缀的过渡 | 6 / 39 | 32 / 39 |
| 累计图片 Base64 | 5,108,448 B | 7,642,560 B |

分批清退降低了历史变化频率，但更多图片会在两次清退间继续随 HTTP 上传，累计 zstd 载荷约增加 49%。该原型只处理不断追加的序列，尚未覆盖固定图、原图恢复、分叉、压缩、重启和并发。它不是可直接替换生产算法的实现，也没有测到真实 token 缓存收益。

## 4. 已修复的送达记账问题

直连真实上游也复现了 0.1.0 的问题：Codex 收到 `response.completed` 后关闭连接，代理仍等待 HTTP EOF，于是四次成功响应被记为状态 0，两张新图一直保留“未送达”标记。这会影响后续预算和临时原图额度结算。

0.1.1 对未压缩 SSE 识别已转发的完成事件，不依赖 Content-Type。回归测试覆盖断连、分块、失败和不完整事件。真实直连复核为四次 200、零张待送达；原图 MCP 恢复的隔离 CLI 集成仍通过。压缩响应保留旧的完整传输判断，是当前支持边界。

## 5. 下一步的明确范围

1. 把 WebSocket 预览从实验中转层做成可选择的正式模式，补齐断线、重连、并发会话、取消、原图额度和本地缓存恢复。当前原型没有原图取回工具和历史总量清退，因此不应直接接管真实 MV。
2. 对固定提示位置做更多交错次序的对照，分别记录首次请求和后续请求的缓存命中。继续保留总输入、缓存读、缓存写、未缓存、输出、请求数、字节和质量各项指标。
3. 将长历史清退放在明确的重建节点评估；健康的增量连接期间，不必为了减少网络字节每轮改写旧图。服务器上下文预算、视觉质量和 token 成本仍需单独管理。

## 复现入口

在仓库创建开发环境后运行；输出目录应为全新的 `.test-data` 路径。真实实验需要显式 `--run`，每个分组最多八次生成、180 秒；会使用现有账户额度，默认 CI 不执行。

```powershell
.venv\Scripts\python.exe -m experiments.transport_probe --codex '<codex.exe>' --out '.test-data\transport-new'
.venv\Scripts\python.exe -m experiments.retention_probe --out 'reports\retention-new.json'
.venv\Scripts\python.exe -m experiments.live_transport --run --codex '<codex.exe>' --out '.test-data\live-new' --arms websocket http http-preview ws-preview
```

`guard-direct` 测正式 Guard 直连；`guard-stable-note` 只替换提示位置。实验无权修改全局 Codex 路由或系统代理。两次准备失败分别发生在 MCP 进程导入与只读工具声明，已修正并加入检查；失败结果不冒充成功样本。
