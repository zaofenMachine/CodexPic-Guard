# 研究与维护计划

0.1.x 已验证图片预算、原图缓存与恢复、配置回退和基础协议。2026-11-14 完成了 [CLI、真实服务与离线对照](RESEARCH-2026-11-14.md)：优先研究原生 WebSocket + 稳定预览，再评估周期性历史清退。以下尚未进入默认行为。

## 1. 稳定图片保留状态

目前每次从完整输入重新选择保留集。历史总量超过高水位后，每张新图可能使更早的位置从图片变成占位符；当前高/低水位不是跨请求持久化的分批清退状态。这会改变前缀，可能损害模型缓存收益。

研究持久化的图片生命周期、稳定占位符和分批清退时机，验证取回、重试、重复图片与上下文压缩后状态。必须同时观察未缓存输入与视觉恢复行为，不能只优化媒体字节。

新增依据：40 步离线对照中，分批策略使旧图变化事件从 33 次降至 7 次，但累计 zstd 载荷增加约 49%。固定缓存提示位置也值得继续测量；一次真实探针中的未缓存输入由约 4.08 万降至约 1.63 万，仍高于约 0.84 万的控制组，不能宣称成本问题已解决。

## 2. 原生传输与同口径对照

当前代理拒绝 Responses WebSocket 升级，以 HTTP 完整请求执行改写；也拒绝非空 `previous_response_id`。因此它没有解决原生增量协议中的服务端图片生命周期。即使没有图片，HTTP 回退也可能改变性能。

后续至少分开对照：原生传输、同样 HTTP 但不改写图片、HTTP 加预算和 MCP 恢复。记录编码请求字节、总输入、缓存输入、未缓存输入、输出、请求/取图次数、延迟和视觉正确率；VPN 计费需要另行采集，不能由这些数值直接代替。

## 3. 图片目录和长期使用

评估可检索的语义目录，同时控制目录自身长度与错误描述风险。固定图在 Codex 自身压缩后不会被自动重新加入，需验证用户与模型能否可靠取回。

Windows 打包版应用可能具有路径虚拟化。当前使用 `%LOCALAPPDATA%` 的数据路径尚未在所有桌面安装方式下验证，需用实际面板、运行引擎与 CLI 检查它们是否读取同一缓存；这是兼容性待验项，不是已经复现的缺陷。

## 验收边界

历史离线回放的 95.4% 字节减少与一次合成图识别通过，不能证明真实长 MV 的细节审查效果、缓存命中、总费用或长期稳定性。完成以上对照前保持实验阶段和显式启用。
